# 并发基线与异步正确性审计（2026-08-04）

## 结论

单实例下 `/ask` 与 `/agent/run` 在并发 1→8 区间**吞吐近似线性上升、P50 基本不变、错误率为 0**。线程池在这个量级不是瓶颈，单次延迟几乎全部由 LLM 生成时间构成。

审计发现并修复一处真实缺陷：文件上传在 `async def` 里同步写盘，会阻塞整个事件循环。

**这份基线不支持「平均响应 2 秒内」的说法**：`/ask` 的 P50 是 12–16 秒，且其中绝大部分是等待模型返回，提高并发只能提升吞吐，无法降低单次延迟。

## 测量方法

- 工具：`agent_app.scripts.benchmark_concurrency`（httpx + asyncio，约 200 行，**未引入 locust**）
- 与 `rag_app.scripts.benchmark_latency` 的区别：那个在进程内串行调用 `ask_question()` 量单次链路耗时；本工具走真实 HTTP，量并发下的排队行为
- 指标：P50 / P95 使用与其他评测一致的 nearest-rank 算法；吞吐为成功请求数 ÷ 该并发档的墙钟时间
- 失败请求不计入延迟统计，单独计入错误率与错误类型分布
- 环境：本地单进程 uvicorn（无 `--workers`），本地 Qdrant `documents` collection，Ollama `bge-m3` embedding，`kimi-k2.6`

## `/ask`（RAG 单次问答）

命令：

```bash
uv run python -m agent_app.scripts.benchmark_concurrency \
  --url http://127.0.0.1:8001/ask --levels 1,2,4,8 --requests-per-level 8
```

| 并发 | P50 | P95 | 最慢 | 吞吐 | 错误率 |
|---:|---:|---:|---:|---:|---:|
| 1 | 14.177s | 19.508s | 19.508s | 0.065 req/s | 0 |
| 2 | 12.058s | 22.111s | 22.111s | 0.143 req/s | 0 |
| 4 | 14.321s | 18.168s | 18.168s | 0.238 req/s | 0 |
| 8 | 15.945s | 18.726s | 18.726s | 0.427 req/s | 0 |

并发 ×8，吞吐 ×6.6，P50 从 14.2s 变到 15.9s。**没有出现排队拐点。**

## `/agent/run`（多步 Agent 编排）

命令：

```bash
uv run python -m agent_app.scripts.benchmark_concurrency \
  --url http://127.0.0.1:8002/agent/run --levels 1,2,4 --requests-per-level 4
```

| 并发 | P50 | P95 | 吞吐 | 错误率 |
|---:|---:|---:|---:|---:|
| 1 | 47.888s | 55.553s | 0.021 req/s | 0 |
| 2 | 34.091s | 49.525s | 0.053 req/s | 0 |
| 4 | 34.362s | 40.722s | 0.098 req/s | 0 |

并发 ×4，吞吐 ×4.7。并发 1 的 P50（47.9s）高于并发 2 和 4，这是 4 次样本下的正常波动，**不应解读为「并发越高越快」**。

## 异步正确性审计

逐个检查两个服务的路由与流式生成器：

| 检查项 | 结论 |
|---|---|
| `/ask`、`/documents/ingest`、`/agent/run`、`/agent/run/stream` 等阻塞型处理函数 | 均为 `def`，由 FastAPI 调度进线程池 ✅ |
| `StreamingResponse` 传入的生成器 | 均为同步生成器，Starlette 用 `iterate_in_threadpool` 包装 ✅ |
| `/health`、`/agent/tools` | `async def` 且不含阻塞 IO ✅ |
| `documents.save_upload_file` | ❌ `async def` 中同步 `mkdir` + `write_bytes` |

### 已修复：上传阻塞事件循环

`rag/src/rag_app/app/routers/documents.py` 原实现在协程里直接 `saved_path.write_bytes(content)`。同步磁盘 IO 发生在事件循环线程上，写盘期间**该进程的所有请求都会停摆**，包括健康检查与进行中的流式响应。批量上传逐个 `await`，N 个文件即 N 次叠加阻塞。

修复方式：抽出 `write_uploaded_bytes`，通过 `run_in_threadpool` 调用。

回归测试 `test_upload_writes_the_file_off_the_event_loop` 的判据是写盘时能否取到运行中的事件循环——取得到即说明跑在 loop 线程上。**该测试已验证会在回退到阻塞写法时失败**（第一版判据用线程名比较，在 TestClient 下恒真，属于无效断言，已重写）。

## 未测量的部分

- **线程池上限未实测。** 本轮尝试用一个廉价同步端点在高并发下探测约 40 线程的默认上限，但两个服务都没有这样的端点（`/agent/tools` 是 `async def`，不经过线程池）。为压测新增端点会改变被测系统，故放弃。结论仅限于「并发 ≤8 时线程池不是瓶颈」。
- **未测并发 >8。** 每次请求都是真实 LLM 调用，更高并发档的成本与耗时不成比例。
- **压测工具目前只发 POST**，无法直接压 GET 端点。当前所有承载业务的端点均为 POST，暂不扩展。
- 单机单进程、无 `--workers`，结果不能外推为生产容量。

## 下一步

数据不支持继续在并发方向优化——瓶颈在 LLM 生成时间，不在编排层。若要降低单次延迟，可选方向按性价比排序：

1. **缓存**（E-2）：相同问题直接命中，把 14 秒降到毫秒级。对演示场景收益最大。
2. **减少生成长度**：当前答案普遍在 800–1300 字，缩短输出能直接缩短生成时间。
3. **换更快的模型**：需重跑答案质量评测确认没有质量回退。

不建议现在做水平扩容或引入消息队列——单实例的瓶颈已经量化清楚，不是并发能力不足。
