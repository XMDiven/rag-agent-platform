## 范围与协议

- 冻结集由独立整理者从已有原文准备 3 题（Docker、PyTorch/Lightning、Ollama/FastChat），1 单源、2 多源。题目与标注先在 `3c23030` 冻结；主实现过程在调参时没有查看内容。
- 每阶段 3 题 × 3 方案 × 2 次，三个阶段共 54 条。两次重复轮换策略顺序，但未完全平衡所有位置。6 道独立问题、每题两次并不等于 12 道独立问题。
- 使用 `kimi-k2.6`、thinking disabled、bge-m3、Qdrant documents、similarity top_k=7、chunk 800/overlap 100。temperature/seed 均未设置，使用供应商默认采样，不能保证确定性复现。
- 每条生成最多 6 次 HTTP、4096 输出 token、单次至多 1024；累计上下文 120000 字节、单次 32000 字节、180 秒。Judge 独立 1 次、1024 输出 token、64000 字节、60 秒。输入预算是 messages + tools 序列化 UTF-8 字节，不是 tokenizer 数量；实际 token 单独记录。
- 用户批准的全实验总上限为 378 次 HTTP、65536 输出 token、8 MiB 上下文。关闭 SDK、生成和检索重试以及本地答案缓存；供应商 token 缓存仍会发生并单列记录。
- Judge 使用相同模型及原有阈值，评分同次最终答案，没有为评分重生成。完成/通过率包含预算失败等全部行；Judge 未调用不算评分通过。来源文件覆盖率独立统计，不等于证据足够支持每个结论。

## 失败分析与唯一改动

基线自动 18/18 通过，但逐条核对保存证据后发现：LoRA/QLoRA 的 6 条回答均有需关注的范围或限定语问题。摘要给出 65B/48GB 以及 full-16-bit 性能主张，同批 [4] 限制章节明确尚未确立 33B/65B 与全量 16-bit 微调性能等效。5 条没有保留此限制；两个 Agent 回答还加入片段未支持的“消费级 GPU”。这属于来源冲突/范围扩大，不宜一概称为完全无来源的捏造。

本轮只改一项：给 RAG 与 Agent 系统提示加入同一条证据策略，保留具体限制、比较基线和 benchmark/规模/硬件/精度条件，不根据先验补齐限定语。未改检索、预算、Judge 或固定流程。

复测中直接 RAG 的 LoRA 两次均保留规模限制（基线 0/2 → 复测 2/2）；已完成的 LoRA 最终答案中保留限制从 1/6 到 4/5。四条回答仍先写宽泛主张再写 caveat，fixed repeat 2 仍遗漏限制；因此只能说限制保留有所改善，不能声称冲突已完全消除。直接 RAG 的局部引用粒度、Agent 的功能归属和少量证据外细节仍有残余风险。以上是代码助手对原文的静态复核，不是人工专家独立评分，也不修改原自动分数。

开发复测 `lora_qlora_compare / agent / repeat 1` 是本轮明确的执行失败：3 次工具决策与 3 次工具内生成用满 6 次，无法再综合最终答案；Judge 未调用。首次检索已包含所需证据和限制，后续又查低秩矩阵与量化技术，内容有重叠但不是相同字面重试。没有检索失败或证据丢失，也没有证据证明 policy 迫使它补检。完整 6 次请求和 3 次检索留在原始记录中，失败计入所有汇总。

固定流程还有独立的开销问题：基线 14 次生成中，8 次子答案完全未进入最终综合输入（11392 输入、1589 输出 token、51688 上下文字节）。本轮没有同时删掉它们，以免把质量策略和执行流程两项改动混在一起。这是测得的可避免工作量，不是已实现的性能收益；也意味着此 fixed 是现有流程对照，不能代表经过优化的固定工作流上限。
